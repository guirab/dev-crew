# T-9 · ajustes dev-crew

_Plano gerado pelo dev-crew. Atualizado em 2026-10-08 17:11 (UTC)._

## Resumo

Deixar o plano mais enxuto na aprovação e mostrar uma barra de progresso nos cards dos agentes. O prompt do Planner passa a pedir frases curtas e a proibir código. Um campo opcional novo, `essential_code`, guarda um exemplo de código só quando ele for essencial. Na tela, resumo, passos/épicos e riscos ficam visíveis e o resto fica recolhido. Os cards Entrevistador, Planner, Developer, Tester e Reviewer ganham uma barra: determinada no Tester e no Reviewer, animada nos outros enquanto estão ativos.

## Por que assim

São duas mudanças pequenas no mesmo front (corpo do plano e card de estágio) mais um campo de contrato. Ao todo são cerca de 12 arquivos, com tipos gerados compartilhados. Dividir só criaria merges em generated.ts e schema.json.

## Passos

1. Adicionar o campo opcional `essential_code: str | None = None` em `Plan` (backend/src/crew/contracts/outputs.py), com um comentário curto: exemplo de código só quando essencial, como contrato de API ou assinatura crítica.
2. Regenerar o contrato pelo fluxo do repo: `uv run python -m crew.cli gen-schema` (atualiza contracts/schema.json) e depois `npm run gen:types` (atualiza frontend/src/contracts/generated.ts). Não editar os gerados à mão.
3. Em backend/src/crew/plan_doc.py, incluir a seção "Código essencial" em bloco de código só quando `essential_code` existir.
4. Reescrever trechos do prompt do Planner (backend/src/crew/agents/prompts/planner.md): frases curtas, objetivas e em linguagem de alto nível, sem trechos de código no plano; o único lugar para código é `essential_code`, quando for realmente essencial. Citar o campo na seção Saída.
5. Em frontend/src/bodies/PlanView.tsx, manter visíveis resumo, passos (ou a lista de épicos) e riscos. Mover arquivos, critérios de aceite, estratégia de testes e "Por que assim" para `<details>`/`<summary>` fechados por padrão, no estilo do `.details` do EpicList. Renderizar `essential_code` em `<pre><code>` só quando existir. Projeto novo e estimativa continuam como estão.
6. Adicionar estilos em frontend/src/bodies/body.module.css: classe para as seções recolhidas e para o bloco de código.
7. Em frontend/src/flow/stages.ts, criar `stageProgress(key, status, counters)`, que devolve `null | { kind: 'determinate', value: number } | { kind: 'indeterminate' }`. Só vale para interviewer, planner, developer, tester e reviewer. idle, pick e skipped (e os outros estágios) devolvem null. done devolve determinada com valor 1. Com status active: tester e reviewer usam a mesma regra de contadores de `stageCounter`, extraída num helper interno comum (n/máx, limitado a 0..1); sem contador > 0, ficam indeterminados. interviewer, planner e developer ficam indeterminados. Em waiting e error, os determinados mantêm a fração e os outros não mostram barra.
8. Em frontend/src/flow/StageCard.tsx, renderizar um componente de barra (div com role="progressbar", e aria-valuenow/aria-valuemax quando determinada) abaixo do texto do header, a partir de `stageProgress`. Usar o `stageKey` só quando não houver `meta` override.
9. Em frontend/src/flow/StageCard.module.css, criar os estilos da barra: trilho, preenchimento verde `var(--accent)` ou equivalente existente, e animação keyframes para o modo indeterminado, respeitando prefers-reduced-motion.
10. Testes: backend em test_contracts.py; front em stages.test.ts, StageCard.test.tsx e um teste de PlanView/ApprovalBody (ver a estratégia de testes).

## Critérios de aceite

- O planner.md pede frases curtas, objetivas e de alto nível e proíbe código no plano, exceto no campo `essential_code` quando for essencial.
- `Plan.essential_code` é opcional e aparece em contracts/schema.json e em generated.ts, gerados pelos comandos do repo. Planos e fixtures sem o campo continuam válidos.
- Na aprovação (waiting), resumo, passos/épicos e riscos ficam visíveis. Arquivos, critérios de aceite, estratégia de testes e justificativa da divisão ficam em seções recolhidas que abrem por clique.
- `essential_code` presente aparece num bloco de código. Quando ausente, nada é renderizado.
- Os cards Entrevistador, Planner, Developer, Tester e Reviewer mostram a barra conforme o status. Aprovação, Concluída e o card de origem não mostram.
- Tester e Reviewer ativos com contador mostram a barra determinada (test_attempt/max_test_attempts, review_round/max_review_rounds). Entrevistador, Planner e Developer ativos mostram a barra indeterminada. O texto do contador continua como hoje.
- Status done mostra a barra cheia. idle e skipped não mostram barra.
- A lógica de contadores não é duplicada: `stageProgress` reutiliza a mesma base de `stageCounter`.
- Sem regressão: `uv run pytest`, `npm test`, `npm run typecheck` e `npm run lint` passam.

## Riscos

- O CLAUDE.md declara os contratos congelados. A tarefa pede o campo explicitamente, mas pode valer registrar a exceção em docs/contract-requests.md e no vault.
- O <details> da aprovação reabre fechado a cada novo snapshot só se o componente for remontado. Usar <details> nativo sem estado controlado, para não fechar enquanto o usuário lê.
- Testes existentes (ApprovalBody.test, EpicPlan.test, EpicsSection.test) podem procurar textos que agora ficam dentro de <details> fechado. No jsdom o conteúdo continua no DOM, mas pode haver ajustes pontuais.

## Estratégia de testes

Backend (backend/tests/test_contracts.py):
- Plan sem `essential_code` valida, com valor None.
- Plan com o campo faz round-trip.
- O schema gerado expõe `essential_code` como opcional.
- Se fizer sentido, plan_doc inclui a seção só quando o campo existe.

Front, função `stageProgress` (frontend/src/flow/stages.test.ts):
- tester/reviewer active com 2/3 → determinada ~0.667.
- Contador 0 → indeterminada.
- interviewer/planner/developer active → indeterminada.
- done → value 1.
- idle/skipped → null.
- approval/done/manual → sempre null.
- Valor limitado a 1 quando n > máx.

StageCard.test.tsx:
- Presença ou ausência de role=progressbar por estágio e status.
- aria-valuenow no modo determinado.

ApprovalBody.test.tsx (com o fixture awaiting_approval):
- Resumo, passos e riscos visíveis.
- Arquivos, critérios, estratégia e \"Por que assim\" dentro de <details> sem atributo open, e abrem ao clicar no summary.
- `essential_code` renderizado num <pre> quando presente e ausente quando não.

Rodar também a suíte inteira: pytest, vitest, typecheck e lint.
